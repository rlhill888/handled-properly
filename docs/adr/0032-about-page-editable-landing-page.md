# /about is an admin-editable landing page again, with a fixed field set instead of Content Blocks

The admin wants `/about` to work as a real landing page: a headshot photo, a row of admin-uploaded social icon buttons that link out, an editable about section, and a list of items the admin sells or wants to promote (image, title, description, optional link) — animated in the same style as the homepage. That reopens the question [`0031`](./0031-about-page-hand-coded-not-block-driven.md) closed by hand-coding `/about` and disconnecting it from `site_about_content`.

We didn't revert to the old approach (`BlockRenderer` reading a generic Content Block array). 0031's objection to that wasn't to admin-editability itself — it was that the admin wanted a *specific* content structure with full design control, not whatever an admin can assemble from the generic block set. That objection still holds. So instead of reviving `blocks` on `site_about_content`, this gives the singleton row two dedicated fields (`headshot_path`, `about_body`) and adds two new flat tables — `site_social_links` (`icon_path`, `url`, `sort_order`) and `site_featured_items` (`title`, `description`, `image_path`, `link_url`, `sort_order`) — each shaped like Trusted Partner rather than a Content Block. The public page (`src/app/about/page.tsx`) stays bespoke JSX + its own CSS module, same as 0031 established; only the specific pieces of copy/media the admin asked to control are now data-driven, everything else (layout, animation, copy chrome like the "ABOUT US"/"FEATURED" eyebrows) stays hand-coded.

The old `blocks` column on `site_about_content` is dropped rather than kept disconnected a second time — 0031 kept it "in case `/about` moves back to being block-driven later"; now that it has, and the answer was a fixed field set instead, there's no remaining scenario where reviving generic blocks for About is on the table. Its one real piece of content (the admin's already-written intro copy, previously living in two Title blocks' `supportingText`) was carried forward into the new `about_body` field by the migration rather than discarded.

`about_body` is plain text (paragraphs split on blank lines), not rich text — the admin only asked to edit "the about section," not format it, and every other admin-editable field here (Social Link's `url`, Featured Item's `title`/`description`/`link_url`) is similarly plain, matching Trusted Partner's fields rather than Content Block's rich-text/HTML-sanitization machinery. If the admin later wants formatting inside the about text, that's a narrower follow-up (a `paragraph`-block-style rich text field) rather than a reason to route back through the general Content Block system.

Social Link's icon is an admin-uploaded image (not a fixed icon-font/platform set) for the same reason Trusted Partner's logo is — we don't want to hardcode which platforms exist or bundle an icon library for ones we don't yet know the admin wants.
